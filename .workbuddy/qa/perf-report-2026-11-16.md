# FeedLore 性能检查报告（2026-11-16）

## 0. 范围与被测版本

| 项 | 内容 |
|---|---|
| 被测程序 | 测试机 `172.26.1.2:3210` 运行中的 `feedlore:b236193`（与本地 `origin/main` HEAD 一致） |
| 数据库 | 测试机 PostgreSQL `feedlore_v2`（`feedlore` 是 1.x legacy，未查） |
| 页面性能 | 本地同版本 `apps/web/dist` + 本地 mock API + 真实 Edge（无头） |
| 排除项 | 生产 `172.26.1.1` 与演示站未触碰；未做写压测、未模拟万人并发 |

方法：容器资源用 `docker stats` 采样 120 点（脚本间隔 5 秒 + 采集开销，实际跨度约 14 分钟）；源站请求用容器内 `fetchFeedRaw()` 对 12 个真实订阅发条件请求；页面用 CDP 采 Navigation/Paint/LCP/Resource Timing，分「冷启动 / 二次加载 / 390px + Fast3G + 4×CPU 降速」三组独立浏览器进程。测量限制：无头 Edge 的资源请求会被浏览器缓存截获（`transferSize=0`），因此**真实传输字节以测试机 curl 实测为准**，CDP 数字用于比较时序。所有临时探针已清理。

## 1. 内存占用（峰值与趋势）

| 指标 | 应用容器 | 数据库容器 |
|---|---|---|
| 采样点数 | 120（约 14 分钟） | 同左 |
| 最小 / 中位数 / 平均 | 196.4 / 209.3 / **212 MiB** | 203.7 / — / ≈211 MiB |
| p90 | 218.8 MiB | — |
| **峰值** | **348.6 MiB** | 237.5 MiB |
| 首 10 点均值 → 末 10 点均值 | 208.7 → 210.8 MiB（**+2.1 MiB**） | 基本持平 |
| CPU 中位 / p90 / 峰值 | 0.07% / 1.67% / 21.04% | 极低 |

**结论**：平稳态约 210 MiB；峰值 348.6 MiB 出现在抓取+AI 定时打标叠加时，之后回落到 210 MiB 区间。14 分钟内净增 2.1 MiB，**未观察到持续泄漏**。容器未设内存上限（宿主机 11.65 GiB），当前占用率约 1.8%，无 OOM 风险。

**可优化点（低）**：峰值约为稳态的 1.65 倍，主要来自 Readability 解析原文页（单页 HTML 上限 3 MB）与日报 map-reduce 的 4 路并发。若将来单账号条目数增长一个数量级，可给容器设 `mem_limit` 并把 `FETCH_CONCURRENCY`/`MAP_CONCURRENCY` 配置化，避免峰值无界。

## 2. 缓存命中与失效

| 缓存层 | 策略 | 实测 | 失效条件 |
|---|---|---|---|
| **日报**（`digests`） | `(owner, date)` 唯一，命中直接返回不烧 token | 最近 3 份读取全部命中：**10 / 2 / 318 ms**（后者为冷连接） | 按日期变更；用户点「重新生成」走 force 绕过（代码路径） |
| **Service Worker** | 带哈希 `/assets/*` 缓存优先；HTML/图标网络优先；`/api/*` 不接管 | 二次加载 4 个资源全部由 SW/HTTP 缓存返回，`transferSize=0`、服务端 0 次静态请求；FCP 44 ms / LCP 92 ms | 改 `VERSION`（当前 `feedlore-v2-6`）或文件名哈希变化 |
| **HTTP 静态** | `/assets/*` → `public, max-age=31536000, immutable`；HTML → `no-cache`；API → `no-store` | 真实响应头已确认；发 `If-None-Match: "fake"` 返回 **200**（无 ETag，靠 hash 文件名而非 304） | 重新构建产生新 hash；HTML 每次协商 |
| **全文抓取**（`article_cache`） | 7 天内命中不回源 | 表中 **0 行**（当前账号未开启全文抓取，无数据可命中） | 7 天 TTL / 定期 prune |
| **图片代理**（`image_cache`） | 浏览器 `public, max-age=86400`；服务端缓存表 | 5,332 行 | 7 天 TTL、30 天保留 |
| **RSS 条件请求** | 携带 `If-None-Match` / `If-Modified-Since` | 12 个真实源抽样：**5 个 304（41.7%）**，11/12 带条件头 | 源站自己决定；RSSHub 系与 feedburner 均返回 200 |

**判断**：本地缓存体系（日报 / SW / HTTP / 图片）工作正常，二次访问几乎零网络成本。真正的短板在**回源条件请求的命中率只有 42%** —— 见下一节。

## 3. 对源的请求情况

| 指标 | 实测 |
|---|---|
| 订阅规模 | 91 个启用频道，但只有 **49 个不同 URL**（多账号共享同一订阅） |
| 请求频率 | 调度器每分钟检查到期；全局平均间隔 **351 分钟**；24 小时共 **48 轮**抓取 |
| 每轮数量 | 典型 1–7 个 URL 组；最大一轮 28 组 / 31 个频道 |
| **重复请求** | **未发现**：同 URL 频道先按 `groupKey` 合并成一组（日志 `28 URL groups / 31 feeds` 证明 3 个重复被合并）；另有 `inFlight` 锁与 `ticking` 锁，上一轮未完不并发起下一轮 |
| 响应耗时（12 个真实源抽样） | 平均 **790 ms**，最快 51 ms，最慢 **2,861 ms**（RSSHub 长文订阅）；GitHub releases 304 普遍 435–1,195 ms |
| 条件请求 | 85/91 频道存有 ETag 或 Last-Modified；抽样 12 个源仅 5 个回 304 |
| 轮次耗时分布（24h） | 中位 **1,214 ms**、平均 3,532 ms、p90 3,882 ms、**max 77,801 ms** |

**明显瓶颈**：那一轮 77.8 秒的抓取（6 个 URL）把 p90 从 3.9 秒拉到极端值，原因是单源超时后的指数退避重试叠加。当前 `ticking` 锁会跳过重叠轮次，因此不会雪崩，但用户点「刷新全部」时可能等一分多钟。

**可优化点**：
1. 对明确不认条件头的源（本次抽样中的 4 个 RSSHub + feedburner）降低抓取频率或单独设 `refresh_minutes`，减少全量 XML 传输。
2. 给「刷新全部」提供进度/部分结果展示（当前只有完成后的汇总日志）。
3. 把单源重试的退避上限与总预算做成可配置项，避免个别慢源拖垮整轮。

## 4. 页面加载性能

### 4.1 构建产物

| 资源 | 原始 | gzip 后 | 备注 |
|---|---|---|---|
| `index-*.js`（入口） | 156,472 B | **49,770 B** | 真实测试机响应，TTFB 244 ms、总 490 ms |
| `vendor-*.js` | 223,223 B | 69,160 B | React 等依赖 |
| `index-*.css` | 171,092 B | **29,572 B** | 唯一渲染阻塞资源 |
| `errorText-*.js` | 6,650 B | 3,408 B | 预加载 |
| `AiView-*.js` | 9,896 B | 3,965 B | 按需分包 |
| **合计 dist** | **858 KB** | ≈**156 KB** | HTML 另计 9 KB（gzip） |

真实测试机资源头：`Cache-Control: public, max-age=31536000, immutable`、`Content-Encoding: gzip`、`Vary: Accept-Encoding`，无 ETag（靠内容 hash 文件名）。HTML 为 `no-cache`，API 为 `no-store`。

### 4.2 加载时序（本地 mock，独立 Edge 进程）

| 场景 | TTFB | DCL | load | FCP | LCP | 启动层消失 |
|---|---|---|---|---|---|---|
| 首次加载（禁用 SW，mock 资源 no-store） | 35 ms | 204 ms | 531 ms | **272 ms** | **924 ms** | 849 ms |
| 二次加载（SW + HTTP 缓存命中） | 11 ms | 37 ms | 38 ms | **44 ms** | **92 ms** | 375 ms（含 350 ms 最小展示） |
| 390px + Fast3G(1.6 Mbps/150 ms) + 4×CPU 降速 | 29 ms | 1,625 ms | 2,909 ms | **900 ms** | **3,532 ms** | 2,961 ms |

**资源顺序**：HTML → 同一时刻并发发起 4 个资源（入口 JS、errorText、vendor、CSS），CSS 与 JS 并行下载；CSS 到达后即可首屏绘制。首屏 API 只有 **4 个**：`/api/session`、`/api/feeds`、`/api/entries`、`/api/prefs`，**各 1 次、无重复请求**；`/api/*` 明确不走 SW。

**判断**：桌面冷启动亚秒级 FCP、二次访问近乎瞬时，健康。弱网下 LCP 3.5 秒主要受 156 KB 资源下载 + 150 ms RTT 支配，属于可接受但仍有优化空间。启动层固定展示 350 ms，在极快环境下反而成为「感知延迟」的主要来源（375 ms 里 350 ms 是故意等待）。

**可优化点**：
1. CSS 171 KB 是唯一渲染阻塞资源；可把首屏骨架的样式内联（当前只内联了启动层），其余异步加载，预计弱网 FCP 可再降 300–500 ms。
2. 启动层的最小展示时长在热启动时可跳过（已有缓存命中说明应用秒开），避免「快还要等 350 ms」的错觉。
3. `vendor` 69 KB gzip 主要为 React 运行时；短期收益有限，不建议为这点体积牺牲现有代码结构。

## 5. 汇总：瓶颈优先级

| 级别 | 问题 | 证据 | 建议 |
|---|---|---|---|
| **P1** | 回源条件请求命中率低（42%），且存在 78 秒长尾轮次 | 12 源抽样 5 个 304；24h 最大 77.8 s vs 中位 1.2 s | 对不认条件头的源单独降频；退避上限配置化；刷新给进度 |
| **P2** | CSS 阻塞首屏 + 启动层固定 350 ms | CSS 171 KB；弱网 LCP 3.5 s；热启动 375 ms 中 350 ms 为等待 | 关键 CSS 内联、热启动跳过最小展示 |
| **P3** | 内存峰值 348.6 MiB（稳态 1.65×） | 120 点采样，净增仅 2.1 MiB | 容器加内存上限；并发度配置化，防未来增长 |
| 非问题 | 重复请求 / 缓存串号 / 内存泄漏 | 91 频道合并为 49 URL；API 不进 SW；首末均值 +2.1 MiB | 保持现状 |

原始采样数据：`.workbuddy/qa/mem-sample.csv`；可复现脚本：`.workbuddy/ui-lab/perf-page.mjs`（`node perf-page.mjs cold|warm|mobile [--no-sw]`）。
