一、结论先说

功能与性能层面可以放心，安全层面有一个必须先修的口子。

57 个场景里 59 个符合预期。数据隔离、SQL 注入、路径穿越、XSS、会话伪造这几类最容易出事的点都守住了，性能也远超目标（1 万条条目 p95 32ms）。

但发现 1 个未授权远程 DoS：一个畸形 Cookie 就能让 Node 进程因 URIError 崩溃重启 —— 已实测容器 RestartCount 从 0 变 1。这个问题不需要账号、不需要构造复杂请求，建议列为发版阻断项。

其次是三处 SSRF（订阅地址 / Webhook / 模型 BaseURL）都只校验协议不校验主机，已实测能打通本机端口与链路本地地址；再往下是登录限流误伤全站、健康检查谎报、错误响应泄露内部信息这三件「不致命但会咬人」的事。

二、问题清单（按严重程度排序）

P0 致命S-01 · 畸形 Cookie 导致进程崩溃（未授权远程 DoS）

server.js:191 parseCookies / :837 getSession

问题：`parseCookies` 直接对 cookie 值调 `decodeURIComponent`，遇到非法百分号转义抛 `URIError: URI malformed`。该调用发生在请求处理函数最外层的 `try` 之前，异常变成未捕获异常，Node 22 默认终止进程。

实测：curl -H "Cookie: feedlore_sid=%E0%A4%A" /api/health → 连接被断开（HTTP 000）；容器 RestartCount 0→1；日志堆栈 `URIError: URI malformed at parseCookies (/app/server.js:195:48)`。

影响：任何能访问站点的人，一个请求即可反复打挂服务（重启风暴，watchtower/编排层会看到不断重启）。不需要账号。

修复建议：

// 1) 解析失败不要抛，交给验签拒绝
function parseCookies(req) {
  const out = {};
  for (const part of String(req.headers.cookie || '').split(';')) {
    const i = part.indexOf('=');
    if (i < 0) continue;
    let v = part.slice(i + 1).trim();
    try { v = decodeURIComponent(v); } catch (_) { /* 原样保留 */ }
    out[part.slice(0, i).trim()] = v;
  }
  return out;
}

// 2) 会话解析移进 try，别让它在护栏之外
const server = http.createServer(async (req, res) => {
  try {
    const session = settings ? getSession(req) : null;
    const user = userOf(session);
    ...
  } catch (err) { /* 统一 500 */ }
});

// 3) 最后一道：进程级兜底，记录而不是退出
process.on('uncaughtException', (e) => logErr('[fatal] 未捕获异常：' + (e && e.stack || e)));
process.on('unhandledRejection', (e) => logErr('[fatal] 未处理拒绝：' + (e && e.stack || e)));

回归用例：新增回归：`parseCookies("feedlore_sid=%E0%A4%A")` 不抛；`GET /api/health` 带畸形 Cookie 返回 200。

P1 高S-02 · SSRF：订阅地址 / Webhook / 模型 BaseURL 三处未做内网校验

rss.js assertFeedUrl · server.js postWebhook · lib/llm.js + /api/digest/test-llm

问题：`isPrivateHost` 只用在图片代理 `/api/img` 一处。新增频道、保存 webhook、测试/生成日报时的 `baseUrl` 都允许任意主机，服务端会真的发起请求。

实测：D1 `http://127.0.0.1:3000/api/health` 38ms 返回「不是可识别的 RSS」（说明已连上自机 3000 端口并拿到 200）；M14 `169.254.169.254` 311ms 同样取到响应；B13 webhook 保存为 `http://127.0.0.1:3000/internal-hook` 成功；D4 test-llm 打到本机 `/api/session` 并带回自站 401 报文。

影响：云主机上可读实例元数据（AK/SK）；可探测内网端口与服务；webhook 可向任意内网地址发 POST。要求已登录（普通账号即可）。

修复建议：

// lib/net.js
const dns = require('dns');
async function assertPublicHost(urlStr) {
  const u = new URL(urlStr);
  if (process.env.ALLOW_PRIVATE_HOSTS !== '1' && isPrivateHost(u.hostname)) {
    throw new Error('不允许访问内网 / 回环地址');
  }
  // 解析后再判 IP，防「域名指向 127.0.0.1」
  const ips = await dns.promises.lookup(u.hostname, { all: true });
  if (process.env.ALLOW_PRIVATE_HOSTS !== '1' && ips.some((x) => isPrivateHost(x.address))) {
    throw new Error('不允许访问内网 / 回环地址');
  }
  return ips[0].address;
}
// 关键：用已解析 IP 建连（防 DNS rebinding），并把 redirect 改成 'manual' 逐跳校验
const dispatcher = new undici.Agent({ connect: { lookup: (h, o, cb) => cb(null, pinnedIp, pinnedIp.includes(':') ? 6 : 4) } });

回归用例：三处各加一条用例：内网地址必须 400；`ALLOW_PRIVATE_HOSTS=1` 时放行（给订阅内网 FreshRSS 的自建用户留口子）。

P2 中S-03 · 登录限流按 socket IP 全局生效，一个人就能锁死所有人

server.js:224-237 loginFails

问题：失败计数键是 `req.socket.remoteAddress`。反向代理（1Panel/OpenResty）后所有请求源 IP 都是 127.0.0.1，于是全站共用一个桶；且不区分用户名。

实测：F2 连续失败 6 次 → 429；F3 紧接着用**正确密码**登录 → 仍然 429「请 60 秒后再试」。

影响：任何人故意输错 6 次密码，全站用户（含管理员）60 秒内都登不进来；脚本可无限续锁，等于关闭登录入口。

修复建议：

// 双维度计数：真实 IP + 用户名；锁定只作用于「该用户名 + 该 IP」组合
const ip = trustProxy() ? (req.headers['x-forwarded-for'] || '').split(',')[0].trim() || req.socket.remoteAddress : req.socket.remoteAddress;
const key = ip + '|' + String(body.username || '').toLowerCase();
// 反代场景加 TRUST_PROXY=1 白名单，只信任来自 127.0.0.1 / 内网网段的 XFF
// 成功登录只清该 key；失败改用指数退避（1s→2s→4s…上限 15min）而不是整段封禁

回归用例：同一 IP 用 A 账号失败 6 次后，B 账号仍可登录；同一账号锁定只影响它自己。

P2 中S-04 · 健康检查谎报健康：数据库掉了仍返回 200 / ready:true

db.js:192-229 status() / server.js:842

问题：`ready` 只在连接成功时置 true，之后任何断开都不会复位；`/api/health` 只读这个内存标志，不做真实探活。

实测：M2 `docker stop` 数据库后：`/api/health` → `200 {"ok":true,"authed":false,"db":{"ready":true,"error":null}}`；同刻 `/api/feeds` → `502 getaddrinfo ENOTFOUND db`。

影响：watchtower / 编排层 / 部署守门全部把「进程活着」当成「服务可用」，DB 故障时不会被发现也不会自愈重试；排障时被误导。

修复建议：

// db.js 暴露真实探活
async function ping() {
  const t = Date.now();
  try { await q('SELECT 1'); ready = true; lastError = null; }
  catch (e) { ready = false; lastError = (e && e.message) || String(e); }
  return { ready, error: lastError, latencyMs: Date.now() - t };
}
// server.js
if (pathname === '/api/health') {
  const st = await db.ping();           // 带 1.5s 超时
  json(res, st.ready ? 200 : 503, { ok: st.ready, authed: !!user, db: { ready: st.ready, latencyMs: st.latencyMs } });
}

回归用例：停库 → health 503；启库 → 自动恢复 200，无需重启进程。

P2 中S-05 · 错误响应把内部细节回吐给客户端，且状态码语义错位

server.js:1649 catch (err) → 502 + String(err.message)；readBody 的 reject 也走这里

问题：所有未分类异常统一 502 并附带原始 message：数据库原文、DNS 主机名、类型转换错误全都会出现在响应里。客户端错误（非法 JSON / 非法参数）也被算成 502。

实测：C1 非法 JSON → `502 {"error":"invalid json"}`；M4 `q=%00` → `502 invalid byte sequence for encoding "UTF8": 0x00`；M5 reorder 脏值 → `502 invalid input syntax for type bigint: "NaN"`；M3 停库 → `502 getaddrinfo ENOTFOUND db`；B18 `date=2026-13-99` → `502 date/time field value out of range`。

影响：泄露表结构 / 列类型 / 内部主机名，给攻击者做错误注入和指纹识别提供反馈；客户端错误返回 5xx 会让前端重试、监控误报。

修复建议：

class HttpError extends Error {
  constructor(status, msg, expose = true) { super(msg); this.status = status; this.expose = expose; }
}
// readBody
if (tooLarge) throw new HttpError(413, '请求体过大');
catch (e) { throw new HttpError(400, '请求体不是合法 JSON'); }
// 外层
const status = err.status || 500;
const msg = err.expose === false || status >= 500 ? '服务器内部错误' : err.message;
logErr('[http] ' + status + ' ' + (err && err.stack || err));   // 细节只进日志
json(res, status, { error: msg, code: err.code || undefined });
// 另：date 用真实日历校验（不要只靠正则），非法直接 400

回归用例：停机、非法 JSON、非法日期、脏 reorder 四种情况分别断言 400/413/503，且响应体不含 `pg` / `ENOTFOUND` / SQL 关键字。

P2 中S-06 · Webhook 允许内网地址（SSRF 子项，独立可修）

lib/prefs.js sanitizeWebhook

问题：只校验 `^https?://` 与长度，不判主机。保存后每次抓取命中规则都会向内网地址 POST。

实测：B13 `POST /api/prefs {webhookUrl:"http://127.0.0.1:3000/internal-hook"}` → 原样保存。

影响：可当作内网 POST 探针（含标题、链接等内容），配合规则还能定时触发。

修复建议：

保存时调用 S-02 的 `assertPublicHost`；对已存的内网地址在发送前再判一次（DNS 可能变化）。

回归用例：保存 `http://127.0.0.1` / `http://10.0.0.1` 应被清空或 400。

P2 中S-07 · 完全没有安全响应头（CSP / nosniff / X-Frame-Options / Referrer-Policy）

server.js json() 与 serveStatic() 的响应头

问题：全站响应只有 Content-Type / Cache-Control。

实测：C9 `GET /` 检测 4 个安全头，命中 0 个。

影响：缺少纵深防御：一旦将来引入富文本/外链资源，XSS 无兜底；页面可被第三方 iframe 嵌套（点击劫持）。当前正文全程纯文本渲染，实际可利用面很小，属「该有但没有」。

修复建议：

const SEC_HEADERS = {
  'X-Content-Type-Options': 'nosniff',
  'X-Frame-Options': 'DENY',
  'Referrer-Policy': 'strict-origin-when-cross-origin',
  'Content-Security-Policy': [
    "default-src 'self'",
    "img-src 'self' data: blob: https:",
    "style-src 'self' 'unsafe-inline'",
    "script-src 'self' 'nonce-<per-request>'",
    "connect-src 'self'",
    "frame-ancestors 'none'",
  ].join('; '),
};
// 注意：首页注入的 window.__APPEARANCE__ 是内联脚本，改成
// <script type="application/json" id="__boot__">{...}</script> + JS 里 JSON.parse(textContent)
// 或给它单独发 nonce，否则只能退化成 script-src 'unsafe-inline'（削弱 CSP 价值）

回归用例：断言 `/`、`/api/feeds`、`/assets/*` 三类响应都带上上述头。

P3 低S-08 · 超大请求体直接断连，客户端拿不到 413

server.js readBody

问题：超过上限时 `reject` 后立刻 `req.destroy()`，响应还没写就断开了。

实测：C2 发送 2MB body → 客户端 `status=0, err=ECONNRESET`（无 JSON、无状态码、服务端无日志）。

影响：前端只能显示「网络错误」，排障困难；也不算规范的 413。

修复建议：

if (data.length > maxBytes) {
  const e = new HttpError(413, '请求体过大');
  req.removeAllListeners('data');
  req.resume();               // 把剩余字节读掉，让连接能正常收尾
  reject(e);
}

回归用例：2MB body → 413 + JSON，连接不被硬断。

P3 低S-09 · 频道重排 / 偏好写入缺少数量与脏值校验

server.js:1010 reorder · :1427 prefs.groupOrder

问题：`reorderFeeds` 直接把客户端数组塞进 VALUES，NaN 留到 PG 才报错；`groupOrder` 不限条数（实测 5000 条照收并落库）。

实测：M5 `id:"abc"` → 502 bigint NaN；巨量 groupOrder → 200 且完整回显 5000 条。

影响：脏值变成 5xx（见 S-05）；超大 prefs 会长期占内存与每次请求的反序列化开销。

修复建议：

const items = raw.filter((x) => x && Number.isFinite(Number(x.id))).slice(0, 500)
  .map((x) => ({ id: Number(x.id), sortOrder: clampInt(x.sortOrder, 0, 0, 1e6), groupName: String(x.groupName || '').slice(0, 40) }));
prefs.groupOrder = list.slice(0, 200);   // 与分组数天然同量级

回归用例：脏 id 被丢弃而不是 5xx；5000 条 groupOrder 截到 200。

P3 低S-10 · 密码策略与默认口令偏弱，且无强制改密

server.js:1506 / :1533 / defaults()

问题：最短 4 位；首次启动播种 `admin/admin`；登录不校验是否仍是默认口令。

实测：codes: 密码 3 位 → 400；4 位 → 通过（B15 与实现一致）。

影响：暴露到公网的自建实例容易被撞库；这也是 S-03 锁死问题的放大器。

修复建议：

最短 8 位 + 常见弱口令黑名单；`ADMIN_PASS` 未设置时启动日志高亮警告；首次登录强制改密（`prefs.mustChangePassword`）。

回归用例：4 位密码被拒；默认口令登录后返回 mustChangePassword=true。

P3 低S-11 · 烧钱/耗时接口没有频率限制

/api/digest/generate、/api/feeds/refresh、/api/watch/apply

问题：仅登录做过限流。日报生成会调外部模型（按 token 计费），手动刷新会打源站，watch/apply 会全库分批判定。

实测：代码审阅（server.js 1618 / 1048 / 1275）：无任何 per-user 节流；仅抓取层有 5s 同 URL 去重。

影响：一个账号（或脚本）可把模型额度刷光、把源站打挂、把 CPU 占满。

修复建议：

按用户加简单的滑动窗口：日报告成 60s 一次、刷新 30s 一次、watch/apply 10s 一次，超限返回 429 + Retry-After。

回归用例：连点两次日报生成，第二次 429。

P3 低S-12 · /api/users 存在 N+1 查询

server.js:1489-1494

问题：对每个账号单独 `db.listFeeds(u.id)` 只为取长度。

实测：E6 3 个账号 14ms；实现为 N 次往返。

影响：当前规模无感，账号数上到几十时接口线性变慢（且每次都在管理员打开用户管理时触发）。

修复建议：

改一条聚合：`SELECT owner_id, count(*) FROM feeds GROUP BY owner_id` 后建 Map 回填。

回归用例：账号数 50 时接口仍 < 50ms。

五、做得对的地方

  • SQL 全部参数化：`q` 与 `tag` 的注入串实测无效，`ORDER BY` 只走白名单字典，`read-all` 的 `feeds=[]` 有「什么都不标」的显式守卫。
  • 会话安全：HMAC-SHA256 签名 + `timingSafeEqual` 定长比较；`exp` / `uid` 双重校验；会话里即使塞 `role:admin` 也不会提权（角色只来自内存注册表）。
  • 多用户隔离完整：跨账号读条目、改标记、改频道、删频道全部 404，`/api/entries` 对别人的数据返回 total=0。
  • 路径穿越不可用：`/../server.js`、`/%2e%2e/`、`/assets/../../`、`/..%2f`、`/....//`、双重编码六种写法一律 404。
  • XSS 面很小：正文/标题/摘要走纯文本管道（`bodyParagraphs` → `

    {text}

    `，React 转义），全仓仅 1 处 `innerHTML` 且已过 `escapeHtml`；外观配置是枚举白名单，首页注入的 `window.__APPEARANCE__` 无逃逸面。
  • 图片代理做了三道拦截：协议白名单、`isPrivateHost`、`data:` 拒收。
  • 输入边界处理普遍扎实：limit 夹到 200、offset 夹到 0、非数字 id 退化为空集、OPML 有 8MB 上限并能区分「空 OPML」与「不是 OPML」。
  • 性能达标：1 万条条目下 `/api/entries` p95 32ms、`/api/entries/flags` p95 11ms、`/api/feeds`（46 频道）p95 22ms、20 并发总耗时 179ms。
  • 首屏体积合理：HTML 5.3KB，CSS 116KB→gzip 20.1KB，业务 JS 208KB→61.9KB，vendor 220KB→67.3KB；带哈希资源 `immutable`、无哈希 `no-cache` 的缓存策略正确。
  • 数据库索引齐备：`entries` 上 9 个索引，含 `title` 的 trgm 索引，模糊搜索不至于全表扫。
